# Nihao web

The Nihao client is a React application with English and Chinese interface text and a single in-memory conversation. User messages can include text and up to four JPEG, PNG, or WebP images; model replies render as Markdown/GFM with KaTeX math and SSE deltas appear as they arrive. User text remains literal. Conversation history stays in the current browser tab and is cleared on reload or New chat.

`src/chat.ts` owns streamed response decoding; `src/App.tsx` owns request cancellation and conversation state. Completed exchanges retain their images in subsequent requests. Failed and stopped assistant replies remain visible but their exchanges are excluded from future model context. New chat aborts an active response and invalidates pending image preparation. All visible text lives in `src/copy.ts`.

`components/MarkdownReply.tsx` loads the Markdown renderer on demand. It supports emphasis, headings, lists, quotes, links, tables, fenced code, `$...$` / `$$...$$` formulas and LaTeX `\(...\)` / `\[...\]` delimiters. Partial streams remain renderable; unsupported formulas fall back to visible source. Wide tables, code and formulas scroll within the reply on phones. Raw HTML and trusted TeX commands are disabled, and model-authored images do not trigger network requests. KaTeX fonts are bundled locally; CSP permits formula style attributes while retaining self-only scripts and stylesheets.

Copy and conversation history preserve original Markdown. Read aloud extracts rendered prose and a single TeX representation of each formula; it does not provide full mathematical verbalization. `npm run test:markdown:ui` exercises streaming, cancellation, phone layouts, copy, mock speech/cache replay and untrusted content using controlled responses, without calling real providers.

Assistant replies have Read aloud, Stop reading, and Replay controls next to Copy. Playback is opt-in and uses the server's Doubao speech endpoint; it never substitutes the browser's built-in voices. `src/speech.ts` validates speech SSE frames and schedules mono 24 kHz PCM through Web Audio as packets arrive. `src/useSpeech.ts` owns one playback session across the conversation, unlocks audio in the user's click handler, and stops both the request and queued audio on cancellation, another playback, a new message, New chat, or unmount. The most recently completed clip up to 8 MiB is kept in memory for replay without another synthesis call. New chat and page reload discard this cache. Total audio per request is capped at 32 MiB. Provider errors render as localized messages without exposing raw provider details.

The image button and clipboard paste accept files up to 20 MiB each. `src/images.ts` checks supported file signatures, decodes locally, and re-encodes as JPEG at a maximum long edge of 2048 pixels and a maximum encoded size of 5 MiB. Transparent areas become white. Local normalization removes source metadata. The browser checks the 12-image and 20 MiB decoded-image conversation limits before sending; the server validates them independently. A failed image remains removable and blocks sending until removed; oversized selections are rejected in full. Images are never written to local storage. Sent thumbnails open a native modal dialog supporting keyboard focus and Escape.

The page follows the supplied DeepSeek screenshot: quiet blue surfaces, generous spacing, a centered title, a wide composer, and small prompt starters. The neutral image button sits in the existing composer toolbar. General web search, video, booking, and other unimplemented capabilities are absent. The prompt starters fill the input; the user sends the message.

Design review follows [unslop](https://github.com/heydamir/unslop) by Damir Sokolovsky (CC BY 4.0), while preserving the user's screenshot direction. Responsive layouts support narrow phones and desktop screens; controls support keyboard focus, IME input, reduced motion, stop, retry, copy, and jump to the latest message.

Read aloud is a quiet text-and-icon action beside Copy; its active state uses the existing blue accent. Preparation stays cancellable, and errors sit below that reply's actions. Playback is never automatic.

Voice input uses a microphone button beside Send. Clicking it requests microphone permission and starts a server-owned Doubao ASR 2.0 real-time session for Chinese and English. `src/dictation.ts` owns capture and the `/api/transcribe` WebSocket, while `src/useDictation.ts` owns one draft snapshot. The self-hosted `public/audio/pcm-capture.js` AudioWorklet downmixes and resamples microphone input to mono 16 kHz PCM16LE, sends 200 ms packets, and reports measured RMS levels. The microphone is not played through the speakers, and recording is capped at two minutes. No browser speech-recognition fallback or stored recording is used.

Streaming transcripts replace only the recording's draft suffix, preserving text and image attachments already in the composer. Finish stops the microphone immediately, flushes the last PCM packet, waits for final recognition, and leaves editable text without sending it. Cancel or Escape restores the previous draft; interrupted sessions retain recognized text and show a localized error. Permission, connection and final-result waits are bounded. Late permission grants, cancellation, New chat, page exit and unmount release microphone tracks and audio contexts. Dictation and read-aloud playback stop one another to avoid recording the assistant's voice.

The dictation design follows the existing unslop direction: Nihao remains a calm, approachable travel companion with blue branding and quiet controls. A small microphone changes the composer toolbar into cancel, status, elapsed time, a compact waveform and a finish checkmark. The waveform is driven only by actual microphone levels and is packed in the center rather than stretched into decorative dots. The existing composer, type scale, icon family and mobile layout stay intact; keyboard focus returns to the draft after finishing or cancellation.

Map-enabled replies use server-supplied structured events alongside streamed text. `src/travel.ts` validates place, route and itinerary data before it reaches `TravelArtifacts.tsx`; assistant text renders independently as Markdown. Place results are expanded by default, route options show estimated duration, distance and transport mode, and one-to-three-day itineraries use a chronological timeline. Navigation links allow only HTTPS `api.map.baidu.com/marker` and `/direction` URLs with known parameters. No browser map API key or embedded map SDK is used.

The current map session token stays only in a React ref and accompanies follow-up requests. New chat clears it; expired-session errors clear it before a retry and explain that previous map facts need to be looked up again. Tool progress is visible while work is running. Artifacts remain staged until nonempty assistant text and a successful `done` event arrive, so cancelled or failed planning never appears as a completed itinerary. Repeated place and route IDs are merged with a twelve-item display limit, and only the newest itinerary in a reply is shown.

Each reply stores the server's `response-language` separately from the interface language. Place names, addresses, hours and directions arrive already translated; map headings, transport modes, units and navigation labels use that reply's language. Switching the header language leaves completed map cards unchanged. During translation the streamed answer remains visible with a localized, cancellable preparation status. Translation failure retains the answer with a retry action and publishes no partial map cards. Links open the external Baidu Maps site, whose interface language is controlled by Baidu.

The map design continues the established unslop direction: quiet white panels, restrained blue links, aligned tabular times and the existing line icons. Long place names and route steps wrap within mobile cards; navigation links move below place details on narrow screens. The language pass preserves this layout and keeps progress and errors within the reply. Validation covers streamed events and cancellation, malformed data, safe navigation URLs and deduplication. Browser QA uses explicit mock SSE responses for error and session flows, opposite interface/reply languages, historical language isolation, translation failure and cancellation; previously captured real Poe/Baidu responses can be replayed separately for desktop/mobile layout checks without another paid API call. Image, playback and dictation regressions remain in the root UI suite.

The root project owns installation, build, tests, and the server. `vite.config.ts` emits the client to `dist/client`; local Vite development proxies HTTP and WebSocket `/api` traffic to `PORT`, defaulting to 8787.
