# Nihao runtime

```text
React text + images → POST /api/chat → isolated Harness Context / Session
                                    → AgentLoop → LlmRuntime → PiAi → Poe
Browser text ← SSE delta events ← agent/assistant-stream text deltas

Read aloud → POST /api/speech { text } → Doubao TTS 2.0 WebSocket
Browser Web Audio ← SSE start/audio/done ← streamed 24 kHz mono PCM

Microphone → AudioWorklet → WS /api/transcribe → Doubao real-time ASR 2.0
Editable draft ← transcript snapshots + final result ← streamed recognition
```

`apps/nihao/server/harness.ts` composes the unchanged upstream `LlmRuntime`, `SessionStore`, `SessionProjectionRegistry`, `SystemPrompt`, `ToolRuntime`, native tool executor, `AgentRegistry`, PiAi provider and `AgentLoop`, plus an app-owned in-memory `AttachmentStore` implementation. When maps are configured, the tool registry contains `search_places`, `place_details`, `route`, and `plan_trip`. Retained filesystem, authorization and other definitions satisfy source dependencies; their providers and tools are not mounted.

The client sends completed user/assistant pairs and its new user message. The server validates roles, alternating order, text and total limits, then imports history into a separate in-memory Session and starts a real Harness turn. The server chooses the persona, provider and model. Browser input cannot supply a system role or tool declarations.

User messages may include `images: [{ name, dataUrl }]`; image-only questions have empty `content`. Only embedded JPEG/PNG/WebP data URLs are accepted. The server checks byte counts, declared format and decoded dimensions, then imports images into a request-local attachment store with random IDs. The PiAi adapter resolves real image bytes from this store and serializes them into Poe image content parts. Historical images travel with completed exchanges. No filesystem attachment provider or image hashing is used, and all image memory is released with the request context.

Only `text-delta` frames from the chat model reach the browser. Independently, the server emits `travel-session`, `tool-status`, `response-language` and `artifact` events on the same SSE connection; raw model tool arguments never become UI data. A completed Harness turn produces `done`; provider failures, timeouts and truncated replies produce a sanitized error. HTTP disconnection propagates cancellation into the active model and map client. Every request disposes its Agent and Cordis context. No database or disk session provider is mounted.

## Maps

`server/maps/baidu.ts` uses the official MCP TypeScript SDK with Streamable HTTP at `https://mcp.map.baidu.com/mcp`. It reads `BAIDU_MAP_API_KEY` only on the server and never exposes the authenticated URL. A request-local client initializes only at the first map call, checks the remote tool list, and calls four allowlisted MCP tools. The current mainland parameter discovered from the live service is `is_chinese_mainland: "true"`. Responses are normalized into bounded `Place`/`Route` records in `shared/travel.ts`; coordinates are explicitly BD-09 and route input strings use latitude then longitude. Transit step alternatives are not concatenated as if they were sequential journeys. Navigation URLs are constructed locally and separately validated by the browser. Calls combine the request cancellation signal with an actual fetch deadline; errors never include provider payloads or key-bearing URLs.

`travel-tools.ts` registers app-owned Harness tools. A route or itinerary may refer only to POI IDs already obtained in the current server-side travel session. `plan_trip` validates all days and IDs before requesting routes, preserves the proposed stop order, and computes arrival/departure times from real route estimates, estimated visits and a buffer. If any day exceeds its finish time, no itinerary is published. It does not solve a global optimization problem or certify opening hours/reservations. Tool and route counts are bounded, with a further 12-model-step guard. The model persona explains these limits and receives the previously committed place/itinerary facts for follow-up edits.

`travel-store.ts` holds up to 100 sessions for two hours of inactivity with a random UUID capability token. Each request obtains an exclusive lock and a detached working copy; commit occurs only when the complete model turn succeeds. Failures/cancellation discard changes. The client retains the token in tab memory, clears it on New chat, and resets it after explicit expiration. The browser stages artifacts until a nonempty textual response and `done` arrive, so cancelled partial plans never appear as completed results. Backend and browser both bound data size; the server keeps at most 80 places and 60 recent routes per session.

`maps/localize.ts` prepares display-only copies after the final assistant response. The server uses the final response's language, excluding intermediate tool commentary, and emits `response-language`. Deduplicated white-listed text slots are translated by an additional `ctx.llm.stream` call through the same Poe adapter. A normally completed response that fails validation can receive one bounded repair request; stream failures, cancellation and source-budget failures are not retried. Numeric placeholders must survive exactly once; structured map facts and links are never writable slots. Slot coverage, lengths, completion, and English outputs without untranslated Han characters are validated before publishing any artifact or committing the session. Translation failure/cancellation leaves the old plan intact. Each browser message retains its response language for map labels, units and buttons independently of the global UI selector. External Baidu pages are outside this localization layer.

Read aloud is an independent, opt-in path; it does not change the Harness chat loop or invoke an audio-input model. `POST /api/speech` validates a nonempty text string up to 20,000 JavaScript string units and a request body up to 128 KiB. `speech-protocol.ts` implements the binary framing from the user's Doubao protocol helpers. `speech.ts` connects to `wss://openspeech.bytedance.com/api/v3/tts/bidirection`, sends the server-only `DOUBAO_API_KEY`, selects resource `seed-tts-2.0`, and creates a fresh connection/session ID for each synthesis. The default speaker is Vivi 2.0 (`zh_female_vv_uranus_bigtts`); `DOUBAO_SPEAKER` can select another compatible voice. No Python subprocess is involved.

The speech route returns SSE `start` metadata (`format: pcm_s16le`, `sampleRate: 24000`, `channels: 1`), base64 `audio` packets, then `done`, or a sanitized `error`. Audio packets are forwarded while synthesis is still running. The browser validates event ordering and PCM framing and schedules each block with Web Audio; it does not buffer the whole response before playback. Finishing synthesis and finishing playback are separate states. The transport bounds output, respects HTTP backpressure, and applies speech-specific concurrency and timeout limits. The server caps PCM output at ten minutes. Disconnection, cancellation and shutdown terminate the upstream synthesis, sending `CancelSession` when a session is active.

`useSpeech.ts` owns one audio session across all reply controls. The click handler creates/resumes the AudioContext so playback respects browser gesture requirements. Stop, another reply's Read aloud, dictation, a new message, New chat and unmount abort the fetch and stop queued audio sources. One successfully played clip up to 8 MiB is cached in browser memory for replay without a second provider call; New chat and reload clear it. The client caps total PCM input at 32 MiB. Neither client nor server persists generated audio. There is no automatic playback or browser-voice fallback.

Microphone dictation is started only by a user gesture. `dictation.ts` owns permission, capture, the WebSocket, timeout and cleanup for a single recording. A self-hosted AudioWorklet (`public/audio/pcm-capture.js`) mixes the microphone channels, resamples continuously to 16 kHz, and produces 200 ms mono PCM16LE packets. The amplitude display is calculated from the actual audio. Finishing stops microphone tracks, flushes the final partial packet, and waits for the provider's final transcript. Cancellation restores the original draft; failures preserve useful partial text. New chat and page exit release capture resources, including streams granted after an earlier permission request was cancelled. Dictation never sends a chat request by itself. Speaking a reply cancels active dictation.

The browser connects to `WS /api/transcribe` on its own origin. The upgrade validates the local hostname and requires an allowed Origin. After the upstream initialization acknowledgement, the server emits `{type:'ready', sampleRate:16000, channels:1}`; the browser then sends binary PCM packets. `{type:'finish'}` ends input and `{type:'cancel'}` aborts it. Server messages are full replacement `{type:'transcript', text, final}` snapshots, followed by `done` once the final provider packet arrives, or a sanitized `{type:'error', code}`. A sentence marked stable by the provider is distinct from the final packet for the whole recording.

`recognition-protocol.ts` implements the gzip binary framing from the supplied `sauc_python` demo. `recognition.ts` uses `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_async`, `X-Api-Key` from `DOUBAO_API_KEY`, and resource `volc.seedasr.sauc.duration`. It enables punctuation, number normalization and a second recognition pass (`enable_nonstream`), with cumulative results (`result_type: full`). It retains only the newest audio packet so the actual final packet can carry the negative sequence and final flag. The route limits recordings to 120 seconds of PCM, uses bounded queues and separate concurrency, and closes the upstream session on disconnect or shutdown. Audio stays in memory and is never logged or saved; no Python runtime is required. This endpoint supports Chinese and English, not the broader language set of `bigmodel_nostream`.

`GET /api/health` returns configuration presence, chat model identity, a `maps` object with provider/configured, a `speech` object with provider/speaker and a `recognition` object with provider/resource, never a credential. Presence does not prove provider authorization. The server reads `POE_API_KEY`, `DOUBAO_API_KEY` and `BAIDU_MAP_API_KEY` from the inherited process environment. API requests reject foreign origins and non-local hostnames. Public hosting is outside this local MVP.

`npm run start:local` and `npm run dev:local` use `scripts/local.zsh` to load the user's existing `poe`/`doubao`/`baidumap` shell aliases or functions when keys are absent. Existing exported values take priority; no key is printed or saved in the project. `npm run env:check` uses the same loading path and reports only presence. Plain `npm start` and `npm run dev` inherit their current environment. The Doubao WebSocket connection separately applies HTTP(S) proxy and `NO_PROXY` settings.

The server build bundles retained Harness source into `dist/server.mjs`; third-party npm libraries remain external. `dist/client` contains the Vite application. Vendor declarations use upstream-compatible compiler settings, while the application and retained Harness package source are checked strictly.
